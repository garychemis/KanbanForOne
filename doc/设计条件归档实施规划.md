# 设计条件归档实施规划

## 1. 目标与边界

“设计条件归档”用于管理不同专业之间相互提交的设计条件，保存条件基本信息、流转关系、图纸量和原始文件，并提供按项目及专业关系的汇总和 Excel 输出。

该功能采用独立模块和独立数据库：主程序只负责依赖注入、导航和日历展示；设计条件数据、附件元数据、候选项、导出和备份均不写入 `Kanban41.db`。

模块位于 `Modules/DesignConditions/`，独立数据位于：

```text
data/design-conditions/
  db/DesignConditions.db
  attachments/{DesignConditionId}/
  staging/
  trash/
  backups/
```

## 2. 字段与日期口径

| 字段 | 数据字段 | 规则 |
| --- | --- | --- |
| 项目 | `ProjectNumber` | 必填，保存时去空格并转大写 |
| 提出专业 | `IssuingDiscipline` | 必填，条件提交方 |
| 接收专业 | `ReceivingDiscipline` | 必填，条件接收方 |
| 接收人 | `Receiver` | 必填 |
| 提出日期 | `IssuedDate` | 必填，唯一日期口径，用于筛选、汇总和日历展示 |
| 条件名称 | `ConditionName` | 必填 |
| 版次 | `Revision` | 文本，支持 `A`、`0`、`Rev.A` 等格式 |
| 图幅 | `DrawingSize` | 多种图幅使用 `|` 分隔，提供 A0～A4 候选并允许输入，自定义值禁止包含 `|` |
| 分图幅数量 | `DrawingCounts` | 与图幅按位置对应的正整数文本，使用 `|` 分隔；新增规格默认数量为 1 |
| 图纸总数量 | `DrawingCount` | 所有分图幅数量之和，正整数 |

数据库 V2 移除旧 `RecordDate` 列，历史记录保留 `IssuedDate`。V3 新增 `DrawingCounts`，将旧记录总数迁移为单项数量明细；日历只根据 `IssuedDate` 纳入显示。

## 3. 数据库

独立库 `DesignConditions.db` 使用自己的 `PRAGMA user_version`、结构校验、WAL 和 checkpoint。首版包含：

- `DesignConditions`：设计条件业务数据。
- `DesignConditionAttachments`：附件元数据，外键级联删除。
- `DesignConditionOptions`：专业、接收人和图幅候选项。

主要索引覆盖提出日期、项目、提出专业、接收专业、条件名称和附件所属条件。

## 4. ViewModel 划分

```text
DesignConditionViewModel
  ├─ 记录查询、筛选和页面统计
  ├─ DesignConditionSummaryViewModel
  └─ 新建、查看、编辑、删除协调

DesignConditionEditorViewModel
  └─ 表单草稿、校验、附件暂存和保存

DesignConditionCalendarSectionViewModel
  └─ 42 天月历摘要、选中日期明细及日历创建入口
```

现有 `MainWindowViewModel` 仅增加模块属性、可见性和导航编排；设计条件业务逻辑不进入主 ViewModel。现有 `CalendarViewModel` 仅持有日历子 ViewModel，不直接依赖设计条件仓储和附件服务。

## 5. 页面与汇总

顶部导航顺序：

```text
看板 | 日历 | 人工时汇总 | 设计条件归档
```

设计条件页面提供“记录列表”和“图纸量汇总”两种视图。列表支持提出日期范围、项目、提出专业、接收专业和关键词筛选，并在页面顶部、工具栏和空状态提供新建入口。

汇总层级为：

```text
项目
└─ 提出专业
   └─ 接收专业
      └─ 设计条件明细
```

前三层输出记录数、图纸数量和附件数量；条件名称、版次、图幅、接收人和提出日期作为明细。

## 6. Excel 输出

使用 ClosedXML 输出：

- `设计条件汇总`：项目、提出专业、接收专业三级小计以及条件明细。
- `设计条件明细`：按一种图幅一行输出当前筛选结果、该规格数量、条件总张数和附件文件名。

多个附件文件名在同一单元格换行，避免因附件拆行造成图纸数量重复。

## 7. 日历集成

日历按当前 42 天网格范围一次查询设计条件摘要，不能逐日查询。月历格显示“条件 n · m张”；选中日期详情显示条件列表和“添加设计条件”入口，新建时自动把选中日期写入 `IssuedDate`。

保存、删除或修改提出日期后发布模块数据变化事件，刷新列表、汇总以及受影响的日历日期。

## 8. 附件与备份

附件使用模块自己的 Repository 和 StorageService。新增文件先进入 `staging`；删除先进入 `trash`；数据库操作失败时恢复文件，避免孤立附件。

模块备份必须在复制数据库前执行自己的 WAL checkpoint，备份包包含：

```text
DesignConditions.db
attachments/
manifest.json
```

恢复设计条件备份不覆盖主数据库、任务附件或人工时配置。

## 9. 验收标准

- 可从设计条件页面和日历新建、查看、编辑、删除记录。
- 可上传、打开、定位和删除多个条件文件。
- 日历只按提出日期显示，并能正确刷新旧日期和新日期。
- UI 和 Excel 的项目/提出专业/接收专业汇总结果一致。
- 设计条件数据库和附件与主业务完全隔离。
- 模块数据库故障不会阻止看板和人工时启动。
- 原有测试全部通过，并新增数据库、仓储、导出和日历测试。

## 10. 实施顺序

1. 独立数据库、模型、仓储和选项。
2. 独立附件生命周期。
3. 列表页面和编辑弹窗。
4. 分级汇总和 Excel 导出。
5. DI、导航和主窗口接入。
6. 日历提出日期接入。
7. 独立备份、测试、README 和版本日志。

## 11. UI 优化记录

- 页面视觉与“人工时汇总”统一：使用相同的页面留白、标题层级、白色面板、轻阴影、指标条和分段视图。
- 筛选区按“提出日期、项目、提出专业、接收专业、关键词”分组并显示常驻标签，避免仅依赖提示信息。
- 日历详情将“新建任务、添加人工时、添加设计条件”分别放入对应分区标题栏，操作与数据上下文直接关联，不再在底部并排挤压。
- 日历格和设计条件卡片采用与人工时记录一致的中性表面、边框和悬停反馈，图纸量使用紧凑指标标签。

## 12. V0.5.0 Review 修复记录

- 保存设计条件时，主体记录、附件元数据和候选项改为单一 SQLite 事务；新增文件先写入 `staging`，删除文件先移入 `trash`，数据库提交成功后再清理垃圾。
- 保存、删除、备份和恢复共用模块级操作协调器，防止多个文件/数据库操作交叉执行。
- 恢复流程先创建保护备份，再校验备份类型、格式版本、数据库版本、SQLite 完整性、重复路径、条目数量、单条目和总解压体积及磁盘空间。
- 恢复交换失败时逐项回滚；回滚不完整则保留恢复现场和保护备份，不再无条件删除旧数据目录。
- SQLite 连接池清理由全局 `ClearAllPools` 改为仅清理设计条件连接池。
- 建表、版本迁移、索引、种子数据和 `user_version` 更新在同一 SQLite 事务内完成。
- 日历异步刷新统一捕获异常；月历摘要使用不加载附件的聚合查询。
- 禁止从设计条件界面直接运行可执行文件和脚本附件。
- 页面、筛选控件、编辑弹窗、附件按钮和日历条件卡片统一采用人工时汇总/人工时详情的表面、圆角、边框、字段高度及交互状态。
